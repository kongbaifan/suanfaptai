# 拓扑接口对接说明

面向**外部消费方**（Unity 等客户端）：如何从本平台取到空调系统的拓扑关系并画出来。

> 本文字段形态与实测数据均由直接调用 `analyze_topology` 核对，样例为
> `four_floor_fcu_fresh_air`、`three_floor_twelve_room`、`multi_zone_all_air`。
> 接口完整字段语义见 [接口文档.md](接口文档.md)，本文只讲拓扑这一条链路。

## 1. 两个数据源，各有用途

| 用途 | 接口 | 说明 |
| --- | --- | --- |
| **画结构** | `GET /api/v1/projects/{project_id}` | 取 `project` 字段，是项目的原始拓扑：节点、边、房间绑定 |
| **画判定** | `POST /api/v1/topology/analyze` | 请求体就是上面那份 `project`，返回连通性、环路、路径、逐管段流量 |

只想看结构用第一个；要标注"哪条路径完整、哪个节点悬空、水环闭没闭、管段流量多大"用第二个——这些图算法后端已经做完了，不必自己实现。

不带项目库直接拿样例：`GET /api/v1/project/sample/{sample_name}`，返回同样形状的项目数据。可用名称 10 个：

```
air  bad  complete  ducted_fresh_air  four_floor_fcu_fresh_air
manifold_fcu  manifold_fcu_dual_water  multi_floor
multi_zone_all_air  three_floor_twelve_room
```

`bad` 是**故意损坏**的样例，用于演示报错。

## 2. 原始拓扑的形状

图的构成：**节点 = `devices` ∪ `pipes`**（两者共用一个 ID 命名空间，不可重名），**边 = `connections`**。

```json
{
  "floors": [
    { "id": "B1F", "name": "地下一层机房", "level": -1,
      "elevation_m": -4.5, "height_m": 4.5 }
  ],
  "rooms": [
    { "id": "office_f1", "name": "一层办公区", "floor_id": "F1",
      "device_ids": ["fcu_f1", "fau_f1"],
      "area_m2": 180.0, "people": 30, "purpose": "office" }
  ],
  "devices": [
    { "id": "chiller_b1", "type": "冷源机组", "name": "SCWE-90H+B",
      "floor_id": "B1F", "location_type": "equipment_room",
      "capacity_kw": null, "flow_m3_h": null, "head_m": null,
      "power_kw": null, "pressure_drop_pa": null, "quantity": 1 }
  ],
  "pipes": [
    { "id": "chw_supply_riser", "system": "chilled_water",
      "pipe_type": "riser_supply",
      "floor_id": null, "from_floor_id": "B1F", "to_floor_id": "F3",
      "length_m": 16.5, "flow_m3_h": null,
      "diameter_mm": 100.0, "width_mm": null, "height_mm": null,
      "local_resistance_coefficient": 2.0 }
  ],
  "connections": [
    { "from_id": "chw_supply_riser", "to_id": "chw_branch_supply_f1",
      "system": "chilled_water" }
  ],
  "simultaneity_factor": 0.9,
  "safety_factor": 1.1,
  "design_options": {},
  "system_form": null
}
```

**枚举取值**（`system` 与 `pipe_type` 都是后端 `Literal`，越界会 422）：

- `system`：`chilled_water`（冷冻水）· `cooling_water`（冷却水）· `hot_water`（热水）· `air`（空气）
- `pipe_type`：`main_supply` · `main_return` · `branch_supply` · `branch_return` · `terminal_branch` · `riser_supply` · `riser_return` · `bypass` · `unknown`（默认）
- `system_form`：`fcu_fresh_air` · `all_air` · `null`（未声明，全部内置样例都是 `null`）

**分层与竖向**：水平管段给 `floor_id`；立管给 `from_floor_id` / `to_floor_id`，`floor_id` 为 `null`。据此即可把管段摆到对应楼层或跨层连接。`rooms[]` 只有 3 个字段在示例里显示，实际共 23 个（其余是负荷计算参数：各项指标、室内外温湿度、围护参数等）。

**设备额定值几乎总是 `null`，这是正常设计**：项目只声明型号名，额定值由后端从设备目录解析。要额定参数走 `GET /api/v1/projects/{project_id}/devices/rated`，它额外给出 `role`、`source`（目录命中还是降级回退）与 `degraded_fields`。

## 3. 分析结果的形状

`POST /api/v1/topology/analyze` 返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `node_count` | int | 节点总数（设备 + 管段） |
| `edge_count_by_system` | dict | 各系统边数 |
| `components_by_system` | dict→list[list[str]] | 各系统的连通分量，每个分量是**排序后**的成员 ID 列表 |
| `loop_count_by_system` | dict | 各系统独立环路数（水环是否闭合看这个） |
| `open_nodes_by_system` | dict→list[str] | 各系统的开口端节点 |
| `isolated_nodes` | list[str] | 完全没有任何连接的节点 |
| `paths` | list | 关键路径，见下文 |
| `pipe_flow_m3_h` | dict→float | **逐管段流量**（算出来的） |
| `floor_summary` | dict | 每层面积/人数/房间数/设备数/管段数/立管数 |
| `vertical_network` | dict | `risers[]`，每条立管带 `served_floor_ids` |
| `issues` | list | 拓扑问题（含 `level`/`code`/`message`/`target`） |

`paths[]` 每条给有序节点串，适合做高亮：

```json
{ "system": "chilled_water", "name": "cold_source_pump_terminal",
  "nodes": ["chiller_b1", "chw_pump_b1", "chw_main_supply_b1",
            "chw_supply_riser", "chw_branch_supply_f1", "fcu_f1"],
  "floor_ids": ["B1F", "F1"], "complete": true }
```

`vertical_network.risers[]`：

```json
{ "pipe_id": "chw_supply_riser", "system": "chilled_water",
  "pipe_type": "riser_supply", "from_floor_id": "B1F", "to_floor_id": "F3",
  "served_floor_ids": ["B1F", "F1", "F2", "F3"] }
```

## 4. 五个必须知道的坑

### 4.1 字典的键**不保证四个系统都在**

`edge_count_by_system` / `loop_count_by_system` / `open_nodes_by_system` / `components_by_system` **只包含实际有边的系统**（`topology.py:37-46, 56-57`）。实测 `three_floor_twelve_room` 整个没有 `hot_water` 键。

**消费方必须用带默认值的取法**（`.get(system, 0)` / `?? 0`），不能假定键存在，否则会抛 KeyError。

### 4.2 `paths` 不是完整路径集，而且**没有热水路径**

后端只有 3 个路径生成器（`topology.py:130-138`）：

| system | name | 语义 |
| --- | --- | --- |
| `chilled_water` | `cold_source_pump_terminal` | 冷源 → 泵 → 末端 |
| `cooling_water` | `cold_source_cooling_tower` | 冷源 → 冷却塔 |
| `air` | `terminal_air_path` | 末端 → 风管 |

**热水系统压根没有路径生成器**。实测 `four_floor_fcu_fresh_air` 热水有 19 条边、3 个环路，`paths` 里依然一条热水路径都没有。

另外 `paths` 长度是 **2 或 3**：冷冻水与冷却水两条**无论是否走通都会出现**（走不通则 `nodes` 为空、`complete: false`），空气那条**只在走通时才出现**。所以判断"有没有风路"要看是否存在该条目，判断"水路通不通"要看 `complete`。

要枚举全部路径，自己从 `connections` 走图，或用 `components_by_system` 做分组。

### 4.3 邻接图是**无向**的，且会静默丢弃悬空边

`_build_adjacency`（`topology.py:69-76`）把每条连接按双向加入，所以连通性、环路、开口端全部是无向口径。**方向信息只在原始 `connections` 的 `from_id`/`to_id` 里**，要画箭头得用原始数据。

同时，`from_id` 或 `to_id` 不在节点集合里的连接会被**直接跳过**，不报错。消费方若自己拼装项目数据，拼错 ID 的边会无声消失。

### 4.4 `open_nodes` 的判据是"度恰好为 1"

`_open_nodes_for_system`（`topology.py:108-114`）只收该系统内度为 **1** 的节点。度为 0 的节点**不算开口端**（它进 `isolated_nodes`）。

**开口端不等于错误**：室外取风口本身就该是开口。实测 `four_floor_fcu_fresh_air` 的 `open_nodes_by_system.air` 是 `["outdoor_air_intake"]`，而该样例 `issues` 为 0。判断真有问题要看 `issues`，不要自己按开口端下结论。

### 4.5 流量只在分析结果里，原始数据是 `null`

原始 `pipes[].flow_m3_h` 实测**全是 `null`**；`pipe_flow_m3_h` 是分析时按负荷算出来的。要按流量画线宽/配色，必须用 `POST /topology/analyze` 的结果。

实测 `four_floor_fcu_fresh_air`：主管 21.028 m³/h，三层支管 6.432 / 7.669 / 6.927，**供回严格相等**。

## 5. 三个样例的实测数据

| | `four_floor_fcu_fresh_air` | `three_floor_twelve_room` | `multi_zone_all_air` |
| --- | --- | --- | --- |
| 楼层 / 房间 | 4 / 6 | 5 / 12 | 3 / 3 |
| 设备 / 管段 / 连接 | 15 / 49 / 83 | 16 / 37 / 67 | 13 / 20 / 38 |
| 设计冷 / 热负荷 kW | 122.3 / 78.5 | 165.5 / 104.6 | 61.4 / 37.6 |
| `node_count` | 64 | 53 | 33 |
| 边数（冷冻/冷却/热/风） | 29 / 7 / 19 / 28 | 29 / 7 / **无键** / 31 | 7 / 5 / 7 / 19 |
| 环路数（同序） | 6 / 1 / 3 / 3 | 6 / 1 / **无键** / 3 | 1 / 1 / 1 / 3 |
| 连通分量成员数 | 24 / 7 / 17 / 26 | 24 / 7 / — / 29 | 7 / 5 / 7 / 17 |
| `isolated_nodes` | 0 | 0 | 0 |
| `open_nodes` | air: 取风口 1 个 | air: 取风口 1 个 | **全空** |
| `pipe_flow_m3_h` 项数 | 49 | 37 | 20 |
| `vertical_network.risers` | 9 | 5 | **0** |
| `paths` | 3 | 3 | 3 |
| `issues` | **0** | **0** | **0** |

各系统都只有 **1 个连通分量**，即三个样例的水环与风路都是完整的。

选样建议：

- **`four_floor_fcu_fresh_air`** —— 结构最规整、四个系统齐全、9 条立管，演示分层与竖向最合适。
- **`three_floor_twelve_room`** —— 规模最大（12 房间），但**没有热水系统**，正好用来验证消费方对"缺系统键"的容错。
- **`multi_zone_all_air`** —— 全空气制式，**立管 0 条**（3 层楼但无跨层管段），风侧边数占比最高，用来验证"无立管"分支。

> 注意 `multi_zone_all_air` 的 `system_form` 实测是 `null`——**全部内置样例都未声明制式**，不要靠这个字段判断它是全空气系统，要看设备构成（该样例含 `组合式空调机组`，无风机盘管）。

## 6. 最小消费流程

```
1. GET  /api/v1/project/sample/four_floor_fcu_fresh_air   → project
   （或 GET /api/v1/projects/{id} 取 .project）
2. 建图：节点 = project.devices ∪ project.pipes
         边   = project.connections（from_id → to_id，有向）
         分层 = pipe.floor_id，跨层 = pipe.from_floor_id/to_floor_id
3. POST /api/v1/topology/analyze   body = project
   → 用 pipe_flow_m3_h 定线宽，paths 做高亮，
     components/loop_count 标连通与环路，issues 标问题
4.（可选）GET /api/v1/projects/{id}/devices/rated → 设备额定参数与降级来源
```

两个接口都是**只读**：不落盘、不创建仿真会话、不写历史。

## 7. 部署提醒

当前全部接口**没有任何鉴权**，其中 `PUT /api/v1/catalog/equipment` 是设备目录**整表替换且不做数据校验**。仅在 `127.0.0.1` 上演示没有问题；一旦开放到局域网供其他客户端访问，这组写接口需要先加访问控制。
