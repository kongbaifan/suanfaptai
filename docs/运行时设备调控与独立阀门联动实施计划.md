> 此文保留原实施规划。当前实现已扩展到冷冻水、热水、冷却水和风路，代码、契约、算法边界以 [连接驱动动态仿真](连接驱动动态仿真.md) 为准。下文“待实施”和拟新增字段是原规划状态。

## 1. 交付目标

外部程序或前端在仿真运行中，通过现有设备控制接口改变阀门开度、设备启停、转速和温度设定；仿真在下一计算步采用这些控制量，并返回一致、可解释的设备、管路和房间结果。

首期重点补齐独立水阀的计算链路：

~~~text
REST 控制请求
  → 校验设备、字段和范围
  → 更新会话控制值
  → 下一计算步冻结有效控制
  → 更新阀门通断、阻力及流量约束
  → 求得支路、主管和水泵实际流量
  → 更新末端换热、供回水温度和房间状态
  → 发布同一计算步的 REST / WebSocket 结果
~~~

首期的核心验收场景：关闭一个无旁通支路上的独立水阀后，下一步该支路流量和末端水侧换热量归零；房间温度按热惯性继续变化；其他支路保持可运行；重新开启阀门后恢复通流。

## 3. 范围和阶段边界

| 阶段 | 纳入范围 | 交付边界 |
| --- | --- | --- |
| P0：首期完整交付 | 冷冻水、热水；独立可调水阀；供水阀、回水阀、串联阀、共享主管阀；树状供回水分配；现有设备控制回归 | 每个受支持末端具有可判定的供回通路；不包含产生多条替代水路的旁通和网状回路 |
| P1：冷却水扩展 | 冷却水阀门、冷机和冷却塔流量关联、断流对制冷能力的反馈 | 先完成可明确识别的单环路，再与 P2 对接复杂分支 |
| P2：复杂水网扩展 | 旁通、交叉连接、多路径、多泵耦合、压差驱动的流量分配、止回阀方向及开启条件 | 建立真正的网络压降约束和泵工作点求解，替代适用范围外的等效分流 |
| P3：风系统扩展 | 风阀、防火阀、风量重分配、风机及末端空气侧反馈 | 结合现有定风量制式明确工况；风阀调节不自动意味着支持完整变风量系统 |

P0 继续使用教学级等效模型，但必须满足通断、流量约束、守恒和明确的适用边界。现有普通支路的并联分配属于 P0；同一末端存在旁通或多条替代路径的情况属于 P2。

遇到超出当前阶段范围的拓扑，应报告可定位到设备或组件的诊断，并明确物理联动未受支持。仿真仍遵循现有对不完整教学项目的容错启动规则，不因新增阀门功能把所有不完整项目都改为无法启动。

本计划默认对接方通过 REST 下发仿真控制，WebSocket 订阅结果。批量控制、跨设备同一步原子生效、真实楼控协议及硬件通讯需要单独的需求和接口设计，不计入 P0。

## 4. 首期技术方案

### 4.1 拓扑与阀门作用范围

在项目适配阶段构建可缓存的水力控制拓扑；每次计算步只更新控制和运行结果。

拟新增内部结构，名称可在实现时按仓库习惯调整：

| 结构 | 最少包含的信息 | 用途 |
| --- | --- | --- |
| WaterControlTopology | 水系统、连通组件、供回方向、节点/连接映射、支持状态 | 隔离水系统与独立组件，识别路径 |
| ValveBinding | 阀门实例 ID、设备类型、所属水系统、所在通路、控制能力 | 将设备控制量对应到实际通路 |
| TerminalHydronicPath | 末端 ID、供水通路、回水通路、经过的管段与阀门 | 判断末端能否形成完整通流条件 |
| SharedFlowConstraint | 共享主管或阀门、受其约束的末端集合、父子关系 | 同一主管约束只施加一次 |
| HydronicFlowResult | 末端流量、管段流量、阀门流量、泵流量、诊断、模型适用状态 | 下游统一消费计算结果 |

具体要求：

1. 设备类型通过既有设备归一与角色表识别，控制能力集中定义，避免再建立分散的设备别名表。
2. 依据 from_id → to_id 和 system 识别通路；不能只用无向连通判断末端可供水，否则可能串到相邻支路。
3. 供水和回水都必须可通。回水阀关闭与供水阀关闭一样，会影响该支路的循环。
4. 同一个主管阀影响其全部下游末端；不同独立组件的泵和流量预算分别计算。
5. 阀门通断在逻辑节点上处理，允许沿用当前单连接点表达；若后续增加显式进口/出口，必须另做项目兼容设计。
6. 阀门数量大于 1 不能推断为串联或并联。P0 对需要联动的阀门要求一个实例表达一个物理位置；数量打包但拓扑不明的阀门给出诊断。
7. 对方向冲突、混接水系统、孤立阀门、多路径和旁通分别给出诊断，不通过取“第一条找到的路径”掩盖歧义。
8. 编辑项目后沿用运行中编辑限制和已有缓存失效流程；控制值变化不重建静态拓扑。

### 4.2 阀门通断与阻力

控制量沿用百分数，不改变单位：

- 独立水阀：opening_pct，范围 0～100，步长 1。
- 末端自带水阀：valve_opening_pct，范围 0～100。
- enabled 为 0 时，可控制阀门的有效开度按关闭处理。
- 多个串联阀门分别参与计算；任何一个完全关闭，且没有替代路径时，整条通路断流。
- 末端自带阀和独立阀不能互相覆盖，也不能把同一阀门影响重复计入。

P0 的阻力曲线可沿用现有 inverse-square 教学关系，即开度比例越小，阻力倍率越大。需要区分两种处理：

- 开度大于 0：使用有界的小开度数值处理，避免除零和溢出。
- 开度等于 0：明确标记通路关闭，实际流量必须为 0；不能只靠一个很大的有限阻力代替关断。

串联阻力相加；共享阀门基于共享通路总流量施加约束，不能把完整主管阻力分别当作每条支路的独立阻力。

当前 RatedSpec 没有完整的阀门 Kv/Cv、执行器和压差曲线字段。P0 使用集中配置、可追溯的教学默认参数，明确标记来源。不能把推定参数标为厂家参数，也不能直接把无量纲 resistance_ratio 当作 Pa 或米水柱。

### 4.3 部分开度必须影响实际流量

现有 allocate_branch_flows 的阻力主要影响分流权重。当泵的可用流量足够，所有末端仍可能得到其流量上限。因此仅修改 weight 无法保证独立阀门能够限流。

P0 同时引入：

1. 末端原有流量上限：保留末端阀位、设备启停、运行台数和模式约束。
2. 独立阀门对应的通路流量上限：根据开度和等效阻力计算。
3. 共享主管或共享阀门的集合上限：受控末端的流量之和不能超过该通路能力。
4. 同一组件的泵可用流量预算：约束该组件全部支路，不借用其他组件的泵流量。

建议采用的教学标定方式：

~~~text
R_ref  = 参考工况下的通路等效阻力
R_now  = 当前开度下的通路等效阻力
Q_ref  = 与参考工况一致的通流能力

部分开度的通流上限：
Q_limit = Q_ref × sqrt(R_ref / R_now)

零开度：
Q_limit = 0
~~~

上述公式是固定参考驱动条件下的教学近似。M0/M2 必须一起确定 Q_ref、阀门参考阻力和泵转速的关系，避免重复乘转速、重复削减末端阀位，或引入没有依据的绝对压差。全开时恢复已冻结的参考基线；开度影响通过通流约束进入分配，不能再次随意乘一遍开度“修正”最终流量。

求解要求：

- 对树状共享关系使用确定性的分层容量约束分配。
- 分支关闭后，剩余支路可在各自上限内重新分配流量。
- 共享主管流量等于其所服务支路流量之和。
- 求解顺序不依赖输入列表顺序，按稳定 ID 排序处理。
- 迭代次数和工作量有上限；不得每步枚举全部简单路径。
- 不支持的非树状共享关系进入诊断流程，不能伪装为已正确求解。

### 4.4 与设备、管路及房间状态衔接

每个计算步只产生一份 HydronicFlowResult：

1. 末端用实际水流量计算换热、出风和水侧回水温。
2. 水泵接收所属组件内的实际流量，继续使用已有运行量和功率模型。
3. 冷热源与系统汇总消费同一流量和换热结果。
4. 管段和阀门的实时流量来自同一通路分配结果；P0 可复用部分现有投影代码，但不能再把开启的阀门当作不透明终点。
5. 管段流速及压降继续使用已有换算；标明其为当前教学模型的派生读数。
6. 房间温湿度按现有动态状态推进，不因控制请求重置。
7. REST 和 WebSocket 投影绑定到同一个会话及计算步。

关闭水阀只直接关断水侧换热。若末端风机仍在运行，其风量和风机功耗可以继续存在；不能把“水侧冷量归零”错误验收为“整个设备所有读数都必须归零”。

P0 无旁通通路的组件，实际泵流量应与末端流量总和一致。到 P2 加入旁通后，应改为泵流量等于末端流量与旁通流量之和，不能沿用过度简化的守恒断言。

### 4.5 不完整或不支持拓扑的结果

拟通过现有 Issue/alarms 通道增加可定位的诊断，代码名称在 M0 冻结，例如：

- SIM_VALVE_UNCONNECTED：阀门未接入有效通路。
- SIM_VALVE_SYSTEM_AMBIGUOUS：阀门所属水系统或方向不明确。
- SIM_VALVE_TOPOLOGY_UNSUPPORTED：当前阶段不支持的多路径或共享关系。
- SIM_VALVE_PARAMETERS_DEGRADED：采用教学默认阀门参数。
- SIM_VALVE_QUANTITY_AMBIGUOUS：数量打包，无法确定物理连接方式。

对超出模型适用范围的组件，保留教学仿真容错行为，但必须附带受限状态。收到开度指令、更新阀门显示值，不等于已经支持该拓扑下的物理联动；前端和接入说明必须区分。

完全关闭的、已识别且受支持的通路必须保持零流量。异常或降级回退不得重新用额定流量给该通路补水。

## 5. 设备类型与控制语义

| 类别 | P0 处理 | 后续处理 |
| --- | --- | --- |
| 球阀、蝶阀、截止阀 | 教学开度调节；支持供回水和共享通路联动 | 有真实曲线后按型号细化 |
| 闸阀 | 支持教学启闭及阻力变化，注明实际调节用途的模型范围 | 按型号能力细化 |
| 止回阀 | 识别为被动方向元件，不新增“手动调开度”的物理承诺 | P2 接入方向、压差及开启条件 |
| 风阀 | 保持能力与当前物理支持状态可区分 | P3 接入风量和风压计算 |
| 防火阀 | 单独定义控制能力，不能直接套用普通水阀规则 | P3 定义关闭工况及风路影响 |
| 末端自带水阀 | 沿用已有控制，参与与独立阀门的串联约束 | 全程回归 |
| 泵、冷却塔、冷热源 | 复用现有控制入口 | 与新增阀门引起的实际流量变化联调 |

现有止回阀等类型也可能被统一控制定义暴露 opening_pct。将其改为只读或移除控制项属于行为兼容变更，必须单独记录、更新 GET controls 和前端测试，并提供明确错误提示。不能在同一个字段上悄悄接受请求但改变其含义。

P0 中阀门开度变化按下一步直接采用，不增加执行器行程时间、迟滞或死区。未来若需要这些动态特性，应新增明确的目标开度与实际开度模型。

## 6. API 契约与接入流程

### 6.1 复用现有路径

| 操作 | 接口 | 约定 |
| --- | --- | --- |
| 查询设备控制能力 | GET /api/v1/realtime/controls/{project_id} | 以返回的字段、范围、步长和类型为准 |
| 启动仿真 | POST /api/v1/realtime/simulate/start/{project_id} | 可带配置；启动后持续推进 |

| 恢复自动控制 | POST /api/v1/realtime/controls/reset/{project_id} | 指定 ID 重置单设备；空对象重置全部 |

调用示例；valve_branch_f1 为后续教学样例中的拟定 ID，实际接入必须使用所选项目的真实设备 ID：

~~~http
POST /api/v1/realtime/control/{project_id}
Content-Type: application/json

{
  "device_instance_id": "valve_branch_f1",
  "values": {
    "opening_pct": 40,
    "enabled": 1
  }
}
~~~

同一个末端自带水阀仍使用 valve_opening_pct；不能与 opening_pct 混用。

### 6.2 必须保留并验证的语义

- 不存在的项目或设备返回 404。
- 不支持的参数、额外顶层字段、非有限值返回 422。
- 有限数值越界继续按当前规则钳制并对齐步长；响应返回服务端实际接受的值。
- 同一请求的所有参数先完整校验，再整体更新；不能部分写入后再报错。
- 手动覆盖仍按设备生效。只改一个参数也会使该设备退出自动调节，其他参数保留当前值。
- 控制优先级延续当前顺序：手动覆盖决定基础控制；故障覆盖其对应字段；模式联锁决定最终允许的有效控制。
- 停止状态可以准备下一次启动的控制值；停止一个正在运行的会话会按现有实现清除手动覆盖。
- 控制值存于运行时会话，不写回项目设计参数，也不承诺服务重启后保留。
- 多个设备的多次 POST 不是原子批量事务；可能分别在不同计算步被采用。
- 对合法但物理联动尚不受支持的设备或拓扑，能力和状态响应应明确说明，避免仅凭 200 宣称已完成物理调控。

### 6.3 “接受”和“采用”的确认机制

以下为拟新增的兼容性字段，并非当前已经存在：

| 位置 | 拟新增字段 | 用途 |
| --- | --- | --- |
| RealtimeControlsResult | session_id、control_revision | 标识接受控制的会话及服务端控制版本 |
| 系统快照 summary | session_id、applied_control_revision | 标识该快照已消费的控制版本 |
| 设备/管段/房间响应 | session_id；继续使用 simcore_tick | 避免把重建前后的相同 tick 当成同一结果 |
| 独立水阀运行值 | flow_m3_h、flow_blocked、hydraulic_effect | 展示流量、通断与物理联动支持情况 |

拟定的字段语义：

- session_id 在真实 SimulationSession 建立时生成；停止后继续使用同一会话时保持不变，布局或受保护初始条件改变导致会话重建时更换。
- 尚无真实会话、仅返回临时 tick-zero 只读快照时，session_id 为 null；不能为了返回编号而创建并缓存会话。
- control_revision 从 0 开始，在同一会话内单调递增；新会话可以重新从 0 开始，因此必须与 session_id 一起判断。
- hydraulic_effect 使用 modeled、unconnected、unsupported 三种值，分别表示已接入当前水力模型、未连入通路、拓扑或类型超出支持范围。参数降级继续使用已有参数来源和诊断字段表达。
- flow_m3_h 对可计算通路返回数值；确认未连接时为 0；不支持且无法可靠计算时为 null，不能用 0 伪装成已确认关闭。
- flow_blocked 仅在通路已判定时返回布尔值；不能判定时为 null。命令开度、有效开度及物理支持状态分别解释，不能互相代替。

保留现有字段的含义：GET controls 的 current 表示控制值，运行快照里的开度或开度比例表示该步采用的有效状态。必要的新增字段只做补充，不重命名现有字段。

control_revision 在接受控制变更或重置后递增。计算步开始时冻结控制版本，完成后发布 applied_control_revision。先于同一步到达、针对同一参数的多次修改，以最后一次接受的值为准；较早值可能被覆盖而未单独运行。

applied_control_revision 证明计算步已经消费该版本，不保证请求值未受模式或故障约束。最终是否物理生效，还要结合有效开度、hydraulic_effect 和相关诊断判断。

### 6.4 并发和快照一致性

- 为同一项目的控制、重置、配置更新、停止和计算步建立明确串行化边界。
- 下一步先取得完整控制快照，再进入数值计算；不得混用一次请求更新前后的参数。
- 不能只依赖字典更新或 Python GIL 作为事务保证。
- 若使用锁，锁不跨网络广播或其他 await；数值计算与命令接受之间的交接必须可测试。
- GET 设备、房间和管段接口继续保持不推进时间、不写历史、不广播的行为。
- 不同时间发起的 REST 请求可以返回不同 tick。测试和前端应按 session_id 与 simcore_tick 对齐，而不是无条件断言任意两个时刻的响应完全相等。

## 9. 测试矩阵

4. 更新冷却水管段和设备读数，确保一个关闭的有效环路不会仍显示额定循环流量。
5. 验证冷却水关闭/复开、冷却泵调速、塔风机转速和其他水系统隔离。
6. 复杂并联冷机、塔及旁通通路交由 P2 的网络约束处理。

### P2：复杂水网与止回阀

1. 先审计现有 Hardy Cross 的单位、压降公式、边模型和固定需求边界，明确可复用的求解组件。
2. 为水泵建立当前转速和运行台数下的工作曲线；缺参数时显式标记教学估算来源。
3. 为阀门建立压降边，并把关闭阀门从可通图中移除或作为严格零流量边。
4. 求解节点连续性和环路压降约束；支持旁通、交叉连接及多条替代路径。
5. 多泵工作点与共享主管在同一模型中求解，不按设备数量机械倍乘总流量。
6. 止回阀由允许方向及压差条件决定通断，处理状态切换的数值稳定性。
7. 规定最大迭代次数、残差阈值、收敛状态及失败诊断。
8. 任何降级结果都必须保留明确关闭通路的零流量约束；禁止回退到会越过关闭阀门的均分结果。
9. 更新旁通参与后的水量与热量混合计算，以及 P0/P1 的守恒断言。

### P3：风阀与防火阀

1. 单独定义空气侧阀门的开度—阻力关系和控制能力。
2. 明确当前定风量制式下风机、静压和风阀调节的边界条件。
3. 让风阀影响实际风量分配，并将结果传到风机、盘管空气侧和房间热湿处理。
4. 防火阀按明确的关闭场景处理受控风路；有关联锁输入时另行定义输入契约。
5. 回风、新风及送风路径分别识别，避免关一个回风阀却误切全部新风。
6. 增加风量守恒、分支隔离、复开恢复和制式兼容测试。
7. 在风量链路验收完成后，再在前端能力说明中标为支持物理联动。
