# 中央空调教学软件后端接口文档

本接口服务面向学生课堂使用的中央空调教学软件。FastAPI 后端负责负荷、风水系统、拓扑、
设备参数、稳态和实时仿真等算法，Vue 工作台负责交互、展示和教学反馈。接口设计优先保证
计算过程可观察、结果可解释，便于学生比较不同系统搭建方案并定位错误。

FastAPI 进程为每个 `project_id` 持有唯一一份仿真 session。Vue 工作台是纯粹的
HTTP / WebSocket 客户端：它不计算任何暖通数值，也不保存权威控制状态。

```text
已存项目 -> 额定参数解析 -> simcore session -> REST 状态
                                    \----> WebSocket 状态
```

控制量提交后立即校验并存下，在下一个仿真 tick 才体现到设备读数里。固定额定值只读。

> 适用边界：接口返回的是工程估算和教学级仿真结果，用于课堂演示、实验和方案理解，
> 不替代正式施工图设计、厂家选型或第三方审图计算。

共 48 个 HTTP 端点 + 1 个 WebSocket。基址默认 `http://127.0.0.1:8010`。

**认证**：当前版本无需认证，所有端点直接调用。生产环境部署时建议在网关层加鉴权。

**并发**：每个 `project_id` 的仿真 session 是单线程的，多并发请求会串行执行。
项目列表、参数库、知识库等只读端点可并发。

**超时**：大型项目（>100 房间）的 `/system/evaluate` 可能需要 10-30 秒，
建议客户端设置 60 秒超时。实时仿真通过 WebSocket 推送，不存在长轮询超时问题。

## 1. 项目管理

项目是「一份 `SystemEvaluateRequest` + 元数据 + 评估历史」的存档，落盘为
`app/data/projects/{project_id}.json`。

### `GET /api/v1/projects`

列出全部项目摘要，按 `updated_at` 倒序。**不支持分页、筛选或排序参数** —— 
返回全量列表，由客户端过滤（前端项目管理面板按名称/描述/标签本地搜索）。

项目管理的完整动作：**新建**（`POST /projects`）、**打开**（`GET /projects/{id}`）、
**重命名**（`PUT /projects/{id}`，沿用当前 project 内容只改元数据）、
**复制**（`POST /projects/{id}/duplicate`）、**删除**（`DELETE /projects/{id}`）。

响应 `ProjectSummary[]`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `project_id` | str | 12 位十六进制 |
| `name` | str | 项目名 |
| `description` | str \| null | 备注 |
| `tags` | str[] | 标签 |
| `created_at` | str | ISO8601，UTC，形如 `2026-09-01T07:04:58Z` |
| `updated_at` | str | 同上 |
| `history_count` | int | 评估历史条数 |

### `POST /api/v1/projects`

新建项目。请求 `ProjectSaveRequest`：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `name` | str | 是 | 项目名 |
| `project` | SystemEvaluateRequest | 是 | 见[第 2 章](#2-输入数据模型) |
| `description` | str \| null | 否 | 备注 |
| `tags` | str[] | 否 | 默认 `[]` |

响应 `ProjectRecord`（= `ProjectSummary` + `project` + `history[]`）。

错误：房间绑定非法返回 **422**，`detail` 为 issue 数组，见[第 10 章](#10-单位与错误约定)。

### `GET /api/v1/projects/{project_id}`

读取单个项目全文，含 `project` 与 `history`（最多 50 条）。

错误：`404` `"Project not found."`

### `PUT /api/v1/projects/{project_id}`

整份回写项目。请求体同 `POST /api/v1/projects`。**没有单独的房间、管段或设备增删
接口** —— 前端改结构一律是读出整份、本地改、整份回写。

两类错误必须区分处理：

- **409** — 该项目的仿真正在运行。`detail` 为
  `{"code": "PROJECT_EDIT_REQUIRES_STOP", "message": "Stop the simulation before editing the project."}`。
  运行状态判定**先于落盘**（见 [main.py:198-203](../app/main.py#L198-L203) 的注释）：
  否则会留下「改动已存、仿真还按旧布局跑」的中间态。停机后同一请求即返回 200。
- **422** — 房间绑定非法，`detail` 为 issue 数组。

### `DELETE /api/v1/projects/{project_id}`

删除项目并清理其运行时资源（停仿真、断订阅、删该项目的历史文件）。响应
`{"deleted": true}`。项目不存在返回 **404**（清理是幂等操作，但删除前仍校验
存在性，避免把"删不存在的项目"变成 500）。

### `POST /api/v1/projects/{project_id}/duplicate`

把项目复制为副本（含楼层/房间/设备/管路与评估历史），副本名形如
`原名 副本`，重名时追加序号（`原名 副本 2`）。响应新建的 `ProjectRecord`；
项目不存在返回 404。用于在样例/既有方案基础上派生新方案，不必从零重建。

### `POST /api/v1/projects/{project_id}/evaluate`

对已存项目跑完整评估，结果写入历史。响应 `SystemEvaluateResult`，
见 [`/api/v1/system/evaluate`](#post-apiv1systemevaluate)。

错误：`404` 项目不存在。

### `GET /api/v1/projects/{project_id}/history`

响应 `ProjectHistoryEntry[]`，最新在前：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `history_id` | str | 12 位十六进制 |
| `project_id` | str | 所属项目 |
| `created_at` | str | ISO8601 |
| `issue_count` | int | 该次评估的 issue 总数 |
| `summary` | dict | 报告摘要（房间数、设备数、冷热负荷等） |
| `result` | dict \| null | 完整评估结果快照 |

### `POST /api/v1/project/validate`

只校验不落盘。请求 `SystemEvaluateRequest`，响应 `ProjectValidationResult`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `valid` | bool | 无 error 级 issue 即为 true |
| `normalized` | SystemEvaluateRequest | 补齐默认值、归一化后的请求 |
| `issues` | Issue[] | 全部问题 |
| `schema_version` | str | 项目结构版本 |

### `GET /api/v1/project/sample/{sample_name}`

取内置样例，返回一份可直接使用的 `SystemEvaluateRequest`。

可用名称：`complete`、`air`、`bad`、`multi_floor`、`manifold_fcu`、
`manifold_fcu_dual_water`、`four_floor_fcu_fresh_air`、`multi_zone_all_air`、
`ducted_fresh_air`、`three_floor_twelve_room`。

`three_floor_twelve_room` 用于多房间制冷教学：包含机房、地上三层与屋面共 5 个楼层节点；
每层 3 间办公室、1 间会议室，共 12 个房间，每层配置 6 台风机盘管与 1 台新风机组。
可用于观察末端分配、水量和室温变化；评估中的风量超出风管尺寸表、风树合流降级与平衡相关提示
仍按现有教学模型解释，不代表工程管网已完成设计校核。

**名称无法识别时不报 404，静默回退到 `complete`。**

样例是通用教学数据，不代表厂商、采购或施工设计承诺。定压补水、水处理、过滤器、
平衡阀与控制阀、冷凝水排放、防火排烟、排风、计量与自动控制均不在简化样例范围内。

## 2. 输入数据模型

### `SystemEvaluateRequest`

所有计算接口（包括项目存储）的数据主体。设计原则：

1. **拓扑是连线表，管段是一等节点** — `connections` 的 `from_id`/`to_id` 可指向设备
   也可指向管段。只在 `pipes[]` 里声明而未被 `connections[]` 引用的管段会被端口图
   静默跳过。
2. **介质成独立子图** — `system` 分 `chilled_water` / `cooling_water` / `hot_water` / `air`
   四选一，每个介质的拓扑独立分析，流量独立分配。
3. **已给的尺寸不改，缺的才反算** — `pipes[i].diameter_mm` 给了就照用，`flow_m3_h`
   三级优先级：拓扑分配的流量 > 你给的值 > 均分兜底。计算结果的 `source` 字段会
   标明该值由何而来：`"input"` / `"standard"` / `"topology"` / `"default"`。

顶层字段：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `floors` | FloorInput[] | `[]` | 楼层 |
| `rooms` | RoomInput[] | `[]` | 房间 |
| `devices` | DeviceInput[] | `[]` | 设备 |
| `pipes` | PipeInput[] | `[]` | 管段 |
| `connections` | ConnectionInput[] | `[]` | 拓扑边（连线） |
| `simultaneity_factor` | float | `0.9` | 同时使用系数，(0, 1] |
| `safety_factor` | float | `1.1` | 安全系数，>0 |
| `design_options` | dict | `{}` | 扩展字段，留给用户存项目级配置 |

## 3. 计算与评估

### `POST /api/v1/system/evaluate`

完整评估，一次算完所有维度。请求 `SystemEvaluateRequest`，响应 `SystemEvaluateResult`：

```
{
  "load": LoadResult,
  "water": WaterResult,
  "air": AirResult,
  "topology": TopologyAnalysisResult,
  "steady_network": SteadyNetworkResult,
  "hydraulic_network": HydraulicNetworkResult,
  "air_network": AirNetworkResult,
  "simulation": SteadyStateSimulationResult,
  "energy": EnergySimulationResult,
  "report": ReportResult,
  "issues": Issue[],
  "recommendations": Recommendation[]
}
```

算法顺序由 `_evaluate` ([main.py:640](../app/main.py#L640)) 固定，**不能颠倒**：

1. **负荷计算** — 只要有 `rooms` 就算，不看拓扑。输出是后续所有步骤的输入。
2. **端口图求解** — `solve_steady_network`：设备按型号展开成端口，管段两端各一端口；
   拓扑校验（孤立端口、供回混接、介质错配、不连通、缺关键设备）；按介质独立分配流量
   （优先 Hardy-Cross，缺源/汇时均分）；守恒残差检查；设备平衡检查（泵扬程、冷机容量）。
3. **系统校验** — `validate_system`：查缺冷源、缺末端、容量不足。
4. **拓扑分析** — `analyze_topology`：图级指标（连通分量、环数、孤立节点、关键路径），
   按分量把流量摊到管段。
5. **需冷量 > 0 才继续** — 短路逻辑：负荷为 0 时后面的水系统、风系统、管网、稳态仿真
   全部跳过，因为没有可分配的流量。
6. **水量/风量** — 按需求与设备额定值算。
7. **水力管网** — 管径、流速、阻力、最不利环路、泵扬程。
8. **风管网络** — 尺寸、流速、阻力。
9. **稳态仿真** — 动态核跑到不动点（[steady.py](../app/simcore/steady.py) 只 116 行，
   本质是 `SimulationSession` 的收敛循环）。
10. **能耗模拟** — 全年工况。
11. **issue 去重、整改建议、报告汇总。**

### `POST /api/v1/load/calculate`

负荷计算。请求 `LoadRequest`：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `rooms` | RoomInput[] | `[]` | 房间 |
| `floors` | FloorInput[] | `[]` | 楼层，用于楼层汇总 |
| `simultaneity_factor` | float | `0.9` | 同时使用系数 |
| `safety_factor` | float | `1.1` | 安全系数 |

响应 `LoadResult`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `total_cooling_kw` | float | 总冷负荷（未乘系数） |
| `total_heating_kw` | float | 总热负荷 |
| `adjusted_cooling_kw` | float | 修正冷负荷（已乘同时系数与安全系数），后续所有计算的输入 |
| `adjusted_heating_kw` | float | 修正热负荷 |
| `rooms` | RoomLoadResult[] | 逐房间负荷 |
| `floor_loads` | FloorLoadResult[] | 逐楼层汇总 |
| `issues` | Issue[] | |

`RoomLoadResult`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | str \| null | 房间 ID |
| `floor_id` | str | 所属楼层 |
| `name` | str | 房间名 |
| `cooling_kw` | float | 冷负荷，等于各冷分项之和（分项法） |
| `heating_kw` | float | 热负荷，等于围护传热 + 新风加热 |
| `fresh_air_m3_h` | float | 新风量 |

| 字段 | 类型 | 说明 |

`RealtimePipeState`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `pipe_id` | str | |
| `system` | str | `chilled_water` / `cooling_water` / `hot_water` |
| `pipe_type` | str | 与 `PipeInput.pipe_type` 一致 |
| `floor_id` | str \| null | |
| `diameter_mm` | float \| null | 项目声明的管径 |
| `flow_m3_h` | float | 当前流量 |
| `velocity_m_s` | float | 流速 |
| `pressure_drop_pa` | float | 管段压降 |
| `head_m` | float | 压降折算的水柱高度 |
| `served_terminal_ids` | str[] | 该管服务的末端；冷却水无末端故为空 |

流量由末端实时水量沿项目连接方向累加得到：供水管取其下游末端之和，回水管取其
上游末端之和，冷却水按单环路取全部环路流量。流速与压降复用
`calculate_water_from_flow`，与静态水力同一套公式。零流量的管三项读数均为 0。

**口径限制**：这是按流量反算，不是压力平衡求解。管段流量完全信任 simcore 的支路
分流结果，本端点只做汇总与换算，因此它看不出"管径过小形成压力壁垒把流量挤到
别处"——那种情况只表现为该管流速偏高。它不替代
`POST /api/v1/hydraulic-network/calculate` 的设计校核，也不是工程平差。两者分工：
静态接口按设计负荷算一次作为选型依据，本端点跟着仿真 tick 走，反映当前阀位与
转速下的实际水量分布。

与 `realtime/rooms` 同为只读投影：仿真未启动时返回不缓存的 tick-zero 快照，
该读取不创建 session、不追加历史、不广播 WebSocket、不写入项目。未知项目返回
404，没有水管的项目返回 HTTP 200 与空列表。

### `GET /api/v1/realtime/devices/{project_id}/{device_id}`

读取单台设备的运行读数，响应结构与上一节相同（`device_count` 恒为 1）。设备 id
不存在返回 404，项目不存在返回 404，未知设备类型返回 422。

与 `realtime/rooms` / `realtime/pipes` 同为只读投影：仿真未启动时返回不缓存的
tick-zero 快照，不创建 session、不追加历史、不广播、不写入项目。

**进风构成按设备类型区分**：一台机组只有一种进风构成，房间所需新风由**唯一一台**
具备新风引入能力的设备承担（新风机组优先，其次组合式空调机组；风机盘管
处理 100% 回风、不引入新风）。若让每台服务该房间的设备各算一份房间新风，
新风负荷会按设备台数成倍放大——风机盘管 + 新风机组共服一室时实测翻了一倍。

若房间**没有任何**具备新风引入能力的设备（例如只配风机盘管却按人数要求新风），
这份新风无处处理，仍按室外状态直接进入房间：负荷不会凭空消失，"缺少新风处理
设备"正是此处应当暴露的结论。

**承担者必须真的能处理新风**：仿真没有直膨模型，任何靠盘管处理新风的机组
都必须接入水系统。若机组只接风口、没有冷冻水/热水，它只是纯风机，`cooling_kw`
恒为 0；房间新风判给它后既不处理新风、房间侧又不再单独注入，新风湿负荷会
**两头落空**。校验器会报 `fresh_air_handler_without_cooling`。

`新风机组` 在目录里是**冷冻水盘管、100% 室外新风**机型（美的 MKS 系列，
新风工况：进风 35/28℃、冷冻水 7/12℃），会自动跟踪各房间的卫生新风量送风，
不随房间冷热需求波动。相关校验规则（`POST /api/v1/project/validate`）：

| 规则码 | 含义 |
|---|---|
| `fresh_air_no_handler` | 房间有新风需求但没有任何组合式/新风机组承担 |
| `fresh_air_handler_without_cooling` | 承担者没有可用冷源（未接冷冻水且仿真无直膨模型） |
| `terminal_oversized` | 房间末端名义冷量超过设计负荷 2.5 倍，阀门失去调节余地 |

**盘管处理混合风（湿度模型口径）**：制冷时盘管处理的是"室外新风 + 回风"
的**混合风**——按送风量等于回风量加新风量做质量平衡，先求服务房间回风的
平均状态，再与室外新风按风量混合，由盘管冷却后得到唯一送风状态
（见 `simcore.devices.coil_leaving_state`）。因此：

- 室外新风的湿负荷**必须经过盘管**，不会被绕过；
- 盘管按焓差自动区分干/湿工况：冷量不足以把送风压到露点则等湿降温（不除湿），
  反之降温除湿、出口落在饱和线上；
- 显热与潜热按同一组焓常数拆分（`cp·ΔT` 与 `Δ(w·(r0+c_pv·T))`），
  两者之和严格等于盘管冷量，不丢能量；
- 一台房间挂多台盘管（如风机盘管 + 新风机组）时，各机组的贡献**逐台累加**，
  不是拿单一送风状态去乘房间总风量。

`SENSIBLE_HEAT_RATIO`（0.75）仅用于"末端有冷量却无送风量"的退化情形与
缺字段参数回填，不再作为运行时除湿份额。

**湿度目标不可达**：模型无再热盘管，而制冷除湿必须把送风压到室内露点以下，
室温因此必然低于目标（过冷量以 `AUTO_DEHUMIDIFICATION_SUBCOOL_C` 为界，
默认 2℃）。若压到该下限仍无法达标（除湿能力不足，或多分区共用末端导致
分配不均），湿度会停在目标之上（并可能被 95% 上限截断），此时：

- `humidity_shortfall_pct` 持续为正，readings 如实反映缺口；
- 快照 `alarms` 出现 `humidity_target_unreachable`；
- 前端实时运行页给出"需配置再热盘管或独立新风除湿"的诊断提示。

## 9. WebSocket

### `WS /ws/realtime/{project_id}`

订阅项目实时状态推送。

**客户端 → 服务端**：连接后发任意文本维持心跳，内容不解析。

**服务端 → 客户端**：JSON 消息，形如 `{"type": "<event_type>", "data": {...}}`。

事件类型：

| `type` | 触发时机 | `data` 内容 |
| --- | --- | --- |
| `"connected"` | WebSocket 握手后立即发送 | `RealtimeSystemState` |
| `"simulation_status"` | 仿真启动/停止 | `{"project_id": str, "running": bool}` |
| `"system_tick"` | 每个 tick 后 | `RealtimeSystemState` |
| `"device_state_updated"` | 设备状态变更（控制、故障等），**增量**事件 | `RealtimeSystemState`，但 `devices` 仅含本次变化的设备（客户端按 `device_id` 合并，见下） |

推送是**单向**的：客户端不能通过 WS 发送控制命令，控制走 `POST /api/v1/realtime/control/{project_id}`。

**增量契约**：`device_state_updated` 只携带本次实际变化的设备（`devices` 为子集），
客户端必须把它**合并**进现有快照，而不是整体替换——否则会丢掉未变化设备的读数。
完整快照由 `connected` / `system_tick` 事件或 `GET /api/v1/realtime/state/{project_id}`
提供。

## 10. 单位与错误约定

### 单位

- 面积 `_m2`：平方米
- 长度 `_m`：米
- 温度 `_c`：摄氏度
- 流量 `_m3_h`：立方米/小时
- 功率/容量 `_kw`：千瓦
- 能耗 `_kwh`：千瓦时
- 压力/阻力 `_pa`：帕斯卡
- 扬程 `_m`：米（水柱）
- 管径 `_mm`：毫米
- 流速 `_m_s`：米/秒

### HTTP 错误

| 状态码 | 场景 | `detail` 形态 |
| --- | --- | --- |
| **400** | 请求语法错误、类型不匹配 | 字符串 |
| **404** | 资源不存在 | 字符串，如 `"Project not found."` |
| **409** | 冲突：运行中编辑项目、运行中改配置 | `{"code": str, "message": str}` |
| **422** | 校验失败 | **三种形态** |

**422 的三种 `detail` 形态**：

1. **字符串** — Pydantic 校验失败，如 `"value is not a valid float"`。
2. **`{code, message, room_id?}`** — 单个业务校验错误，如
   `{"code": "ROOM_BINDING_UNKNOWN", "message": "Room ... references unknown device ...", "room_id": "..."}`。
3. **Issue 数组** — 房间绑定多个问题，或项目校验结果。每个 issue：

   ```
   {
     "code": str,          // ROOM_BINDING_DUPLICATE | ROOM_BINDING_UNKNOWN | ...
     "severity": str,      // "error" | "warning" | "info"
     "message": str,
     "source": {
       "type": str,        // "device" | "pipe" | "room" | "system"
       "id": str,
       "name"?: str
     },
     "context"?: {...}
   }
   ```

**前端必须先判断 `Array.isArray(detail)`，再按数组/对象/字符串分别处理。** 见
[web/src/api/client.ts](../web/src/api/client.ts)。

### Issue 严重级

- `"error"` — 阻塞性错误，必须修复才能继续（如缺冷源、缺末端、房间绑定非法）。
- `"warning"` — 不合理但不阻塞（如容量不足、流速超标、不连通子图）。
- `"info"` — 提示性信息（如优化建议、参数建议）。

### 常见错误码

| 错误码 | 级别 | 说明 |
| --- | --- | --- |
| `ROOM_BINDING_UNKNOWN` | error | 房间 `device_ids` 引用了不存在的设备 |

| `ROOM_BINDING_UNSUPPORTED_DEVICE` | error | 房间列了非末端设备（冷源、水泵等） |

| `MISSING_CHILLER` | error | 缺冷源 |

## 11. 快速开始

### 场景 1：新建项目并评估

```bash
# 1. 获取样例模板
curl http://127.0.0.1:8010/api/v1/project/sample/complete > template.json

# 2. 新建项目
curl -X POST http://127.0.0.1:8010/api/v1/projects \
  -H "Content-Type: application/json" \
  -d '{
    "name": "我的第一个项目",
    "project": '"$(cat template.json)"'
  }' | jq '.project_id' -r > project_id.txt

# 3. 对项目跑评估
curl -X POST http://127.0.0.1:8010/api/v1/projects/$(cat project_id.txt)/evaluate \
  | jq '.issues[] | select(.severity=="error")'
```

### 场景 2：启动实时仿真并订阅

```bash
# 1. 设置仿真配置（首次调用自动创建 session）
curl -X POST http://127.0.0.1:8010/api/v1/realtime/simulate/config/$(cat project_id.txt) \
  -H "Content-Type: application/json" \
  -d '{"mode": "cooling", "tick_interval_sec": 1.0}'

# 2. 启动仿真
curl -X POST http://127.0.0.1:8010/api/v1/realtime/simulate/$(cat project_id.txt)/start

# 3. WebSocket 订阅（需支持 WS 的客户端，如 websocat）
websocat ws://127.0.0.1:8010/ws/realtime/$(cat project_id.txt)
# 每秒收到 {"type":"system_tick", "data":{...}} 推送

# 4. 发送控制指令
curl -X POST http://127.0.0.1:8010/api/v1/realtime/control/$(cat project_id.txt) \
  -H "Content-Type: application/json" \
  -d '{"device_id": "chiller_1", "control_type": "target_supply_temp", "value": 7.0}'

# 5. 停止仿真
curl -X POST http://127.0.0.1:8010/api/v1/realtime/simulate/$(cat project_id.txt)/stop
```

### 场景 3：单次计算（不保存项目）

```bash
# 直接对数据跑评估，不落盘
curl -X POST http://127.0.0.1:8010/api/v1/system/evaluate \
  -H "Content-Type: application/json" \
  -d @template.json \
  | jq '.load.total_cooling_load_kw'
```

### WebSocket 重连建议

实时订阅断线后：

1. 指数退避重连（首次 1s，最多 30s）
2. 重连成功后检查 `GET /api/v1/realtime/simulate/status/{project_id}` 确认仿真是否还在运行
3. 若仿真已停止，重新走 `POST .../start` 流程
4. 收到 `{"type":"connected"}` 后的首条消息即为完整 `RealtimeSystemState`，可直接覆盖本地状态
